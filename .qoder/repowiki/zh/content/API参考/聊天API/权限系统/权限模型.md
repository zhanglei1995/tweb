## 介绍
本文档详细阐述了聊天应用中的权限模型设计。该模型定义了三种核心权限类型：默认成员权限、管理员权限和所有者权限，用于精确控制用户在群组、超级群组和频道中的行为。文档深入解析了每种权限所包含的具体权限项（如发送消息、添加成员、删除消息、编辑聊天信息等）的技术实现，阐明了权限继承机制和优先级规则，并提供了针对不同聊天类型的权限配置最佳实践。此外，文档还记录了权限模型的扩展性设计，为未来添加新的权限类型奠定了基础。

## 权限类型架构
权限模型基于三种核心权限类型构建，形成一个层次化的权限控制系统：
1.  **默认成员权限 (Default Member Permissions)**：定义了聊天中所有普通成员的默认行为限制。这些权限是基础性的，所有成员都受其约束，除非被更高层级的权限覆盖。
2.  **管理员权限 (Administrator Permissions)**：授予特定成员（管理员）超越普通成员的额外权限，使其能够管理聊天。管理员的权限可以被所有者进一步配置和限制。
3.  **所有者权限 (Owner Permissions)**：拥有聊天的最高控制权，可以执行所有操作，包括修改聊天类型、删除聊天以及管理其他管理员。

该架构通过 `ChatBannedRights` 和 `ChatAdminRights` 两种数据结构来实现。`ChatBannedRights` 用于存储被禁止的权限（即默认成员权限），而 `ChatAdminRights` 则用于存储被授予的权限（即管理员权限）。所有者作为创建者，其权限是隐含的，不受这两种结构的直接限制。

## 默认成员权限
默认成员权限通过 `ChatBannedRights` 结构来定义，它是一个包含布尔标志（flags）的对象，用于明确禁止成员执行某些操作。这些权限是“禁止性”的，即未被明确禁止的操作即为允许。

### 具体权限项
根据代码分析，主要的默认成员权限项包括：
*   **发送消息** (`send_plain`): 禁止发送纯文本消息。
*   **发送媒体** (`send_media`): 一个父级权限，包含发送照片、视频、音频、文件、贴纸、GIF、投票等子权限。
*   **邀请用户** (`invite_users`): 禁止通过链接邀请新成员。
*   **固定消息** (`pin_messages`): 禁止固定聊天中的消息。
*   **更改信息** (`change_info`): 禁止更改聊天标题、描述或照片。
*   **管理话题** (`manage_topics`): 在论坛中，禁止创建和管理话题。

这些权限在用户界面中通常以复选框的形式呈现，选中表示“禁止”，未选中表示“允许”。例如，在 `ChatPermissions` 类中，通过 `fields` 数组定义了这些权限项及其对应的用户界面文本。

## 管理员权限
管理员权限通过 `ChatAdminRights` 结构来定义，它同样是一个包含布尔标志的对象，但其含义是“允许性”的，即被设置为 `true` 的权限表示管理员可以执行该操作。

### 具体权限项
管理员权限项根据聊天类型（群组或频道）有所不同：
*   **通用权限**:
    *   **更改信息** (`change_info`): 允许修改聊天信息。
    *   **删除消息** (`delete_messages`): 允许删除任何成员的消息。
    *   **管理通话** (`manage_call`): 允许管理语音或视频通话。
    *   **添加管理员** (`add_admins`): 允许创建新的管理员。
*   **频道特有权限**:
    *   **发布消息** (`post_messages`): 允许在频道中发布消息。
    *   **管理消息** (`manage_messages`): 一个嵌套权限，包含发布、编辑和删除消息。
    *   **管理故事** (`manage_stories`): 允许发布、编辑和删除故事。
    *   **管理直接消息** (`manage_direct_messages`): 允许管理订阅者发送的直接消息。
*   **群组特有权限**:
    *   **封禁用户** (`ban_users`): 允许封禁或踢出成员。
    *   **通过链接添加用户** (`invite_users`): 允许通过邀请链接添加用户。
    *   **固定消息** (`pin_messages`): 允许固定消息。
    *   **匿名发送** (`anonymous`): 允许以聊天身份而非个人身份发送消息。

在 `ChatAdministratorRights` 类中，通过 `construct` 方法根据聊天的 `broadcast` (频道) 和 `forum` (论坛) 标志动态构建了不同的权限列表。

## 所有者权限
所有者权限是最高级别的权限，由聊天的创建者（creator）自动拥有。在代码中，所有者的权限是通过检查 `chat.pFlags.creator` 标志来确定的。

### 权限范围
所有者拥有以下特殊权限，这些权限通常无法授予普通管理员：
*   **更改聊天类型** (`change_type`): 可以将群组升级为超级群组或频道。
*   **删除聊天** (`delete_chat`): 可以永久删除整个聊天。
*   **转让所有权**: 可以将所有者身份转让给其他成员。

在 `hasRights` 函数中，对于 `change_type` 和 `delete_chat` 这类操作，直接返回 `false`，因为只有所有者才能执行这些操作，而所有者的权限检查逻辑在函数开头就已经处理（`if((chat as Chat.chat).pFlags.creator && isCheckingRightsForSelf)`）。

## 权限继承与优先级
权限系统遵循一个清晰的继承和优先级规则，确保权限检查的逻辑一致性。

### 继承机制
权限检查遵循“最小权限”原则。当检查一个用户是否能执行某项操作时，系统会首先确定该用户在聊天中的角色（普通成员、管理员、所有者），然后根据其角色对应的权限集进行判断。

### 优先级规则
权限的优先级从高到低依次为：
1.  **所有者权限**: 最高优先级。所有者可以执行任何操作，不受任何限制。
2.  **管理员权限**: 次高优先级。管理员可以执行其被明确授予的权限，但不能执行所有者专属的操作。
3.  **默认成员权限**: 基础优先级。所有成员（包括管理员和所有者）都受默认成员权限的约束，除非他们的角色权限明确覆盖了这些限制。

例如，`hasRights` 函数中的 `pin_messages` 权限检查逻辑体现了这种优先级：
```typescript
case 'pin_messages': {
  return isAdmin ? !!(myFlags[action] || (!(chat as Chat.channel).pFlags.megagroup && myFlags.post_messages)) : !myFlags[action];
}
```
这段代码的逻辑是：
*   如果用户是管理员 (`isAdmin`)，则检查管理员权限 (`myFlags[action]`) 是否允许固定消息。
*   如果用户不是管理员，则检查默认成员权限 (`myFlags[action]`) 是否禁止固定消息（`!myFlags[action]` 表示未被禁止即为允许）。

这表明管理员的权限可以覆盖默认成员的限制。

## 权限配置最佳实践
根据聊天类型的不同，应采用不同的权限配置策略以达到最佳的管理效果。

### 群组 (Group)
*   **默认配置**: 通常允许所有成员自由发送消息和媒体，以促进交流。可以禁止非管理员成员邀请用户或更改信息，以防止滥用。
*   **管理员配置**: 授予管理员“封禁用户”、“通过链接添加用户”和“固定消息”的权限，以便他们维护秩序。

### 超级群组 (Supergroup)
*   **默认配置**: 可以启用“慢速模式”(Slowmode) 来限制消息发送频率。根据需要，可以限制发送媒体或投票的权限。
*   **管理员配置**: 除了群组的权限外，还可以根据需要授予“删除消息”和“更改信息”的权限。

### 频道 (Channel)
*   **默认配置**: 通常将 `send_messages` 权限设为禁止，使频道成为只读的广播平台。
*   **管理员配置**: 重点配置“管理消息”和“管理故事”等嵌套权限，明确管理员的发布和编辑权限。谨慎授予“添加管理员”权限。

在 `AppGroupPermissionsTab` 类中，通过 `init` 方法实现了对不同聊天类型的权限配置界面，包括默认权限、慢速模式和付费消息设置。

## 扩展性设计
权限模型在设计上具有良好的扩展性，便于未来添加新的权限类型。

### 抽象的权限类型定义
权限类型 `ChatRights` 被定义为一个联合类型，它不仅包含了 `ChatBannedRights` 和 `ChatAdminRights` 中的所有标志，还显式地添加了 `change_type`、`change_permissions`、`delete_chat` 等操作。这种设计使得可以在不修改核心权限结构的情况下，通过添加新的字符串字面量来扩展权限。

### 集中的权限检查逻辑
所有权限检查都集中在 `hasRights` 函数中。当需要添加新的权限时，只需在 `switch` 语句中为新权限添加相应的 `case` 分支，并定义其检查逻辑。这种集中式的设计极大地简化了权限的扩展和维护。

### 动态的UI构建
权限的用户界面是通过代码动态构建的（如 `ChatPermissions` 和 `ChatAdministratorRights` 类中的 `v` 数组）。这意味着添加新的权限项只需要在相应的数组中添加一个新的配置对象，而无需修改UI模板，保证了前后端的一致性。
